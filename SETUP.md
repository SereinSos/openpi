# Setup

Use Pi 0.99.1 or newer and Node.js 22.19.0 or newer. Development dependencies and CI use Pi 1.2.0. Upgrade Pi before installing this OpenPI version. Install the public Pi package:

```sh
pi install npm:@tt-a1i/openpi
```

To inspect the current source before loading it, install directly from GitHub instead:

```sh
pi install git:github.com/openpi-dev/openpi
```

Pi installs the package dependencies automatically. Restart Pi or run `/reload` after installation.

## Optional web search

The repository-owned `extensions/web-search/` Pi extension is off by default. **Settings → Web search** or `/openpi-setup enable web search` sets `web_search_enabled`. Search defaults to the current Session model and reuses Pi's actual protocol, connection, and credentials. It is a provider-hosted tool in the same model request, without a second model/provider stack, independent summary request, external search key, or OpenPI capability group. The model decides when to search. No provider, protocol, or model fallback is performed.

OpenAI Responses/Codex Responses and Anthropic Messages are implemented. Known official endpoint/model combinations are eligible; unsupported protocols and unknown gateways receive no native search tool. A custom connection requires an explicit `web_search_model_support` declaration after verified native execution or the user's explicit capability confirmation: true enables support, false denies support, and null restores automatic detection. The declaration is bound to the exact current provider, model, API, and base URL. API compatibility, a familiar model name, and DeepSeek's consumer website search do not establish hosted-search support. Existing subscription credentials do not establish Anthropic API search entitlement.

Pi owns cancellation, transport, usage, persistence, forks, and compaction. Native output and exact search terminal evidence are retained on the assistant message; citations become clickable links. Only retained messages from the identical connection replay native blocks, including after the feature is disabled. Web projection exposes bounded search activity rather than opaque provider output. Direct/Workflow children exclude the extension, so hosted tools cannot bypass their tool allowlists. Native output and aggregate replay are bounded to 256 KiB; an oversized history requires Session compaction. Anthropic `pause_turn` is an explicit error: automatic protocol continuation is not implemented by this adapter. No webpage cache or stored-content paging system is added.

The legacy `web_access_action` remains for explicit management of an already selected optional Pi package, including native reviewed confirmation and an explicit later reload. It is never a fallback from current-model search. Previously installed external search extensions must be disabled separately to avoid conflicting search tools.

## Response preferences and visible reasoning levels

Settings → Configuration submits response preferences through the existing `/openpi-setup` episode. `response_verbosity` accepts `default`, `low`, `medium`, or `high`; `response_reasoning_summary` accepts `default`, `auto`, `concise`, `detailed`, or `none`. Both default to `default`, which leaves Pi's native request unchanged. Overrides apply only to the parent Session's current model using OpenAI Responses or Codex Responses. Child Sessions retain their native Pi request parameters. A reasoning-summary override additionally requires native reasoning support and existing reasoning parameters. `none` removes only the summary request, preserving effort and other reasoning fields. Other APIs remain unchanged. A compatible API does not establish every model's acceptance of these optional values.

The visible reasoning-level controls are presentation preferences and save directly without a model turn. `web_hidden_thinking_levels` stores a unique list drawn from `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, and `max`; the default `[]` hides none. The picker filters Pi's native available levels while retaining the current selection. It does not add model support or change the Session's native thinking level. Both entry points use the same validated configuration and persistence lifecycle.

## fd, rg, and read-only git tools

The `file-search` extension registers `fd` and `rg` as model tools, and `git-read` registers `git_show`, `git_diff`, and `git_log` (read-only git inspection). They stay outside an ordinary parent turn until the user explicitly asks to use `fd`/`rg`/git history, or structured file search, or the model loads the `search` group through `openpi_load_tools`. Entering or restoring Plan Mode is a runtime-safety exception: it loads `search` for that Session so diff investigation can use the structured Git boundary. The gateway is shown after an explicit OpenPI-capability request, or remains visible when the user opts into adaptive discovery; children receive these tools only when active in the parent and permitted by their role allowlist. No setup is normally needed: at startup `fd`/`rg` silently use a system-installed binary (`fd`/`fdfind` and `rg`) when available, or an existing binary in the agent's private managed bin directory (`~/.pi/agent/bin`). Only when neither exists does it download an official release binary (macOS/Linux, arm64/x64, over HTTPS) into that directory — a persistent cache that survives package updates — and show a one-time notification. If your platform is unsupported, install `fd` and `rg` with your package manager and restart Pi. The git tools require a system `git`.

While Plan Mode is active, raw Bash `git diff`, `git show`, and `git whatchanged` are refused, as are diff-generating `git log` options such as `-p`, `--stat`, `--name-only`, and `-L`. Use `git_log` to find commits and `git_diff` / `git_show` to inspect changes; the latter commands always pass `--no-ext-diff --no-textconv --no-color`, so repository-configured `diff.external` and textconv drivers are not executed. This guarantee is scoped to the Git diff-driver boundary rather than every possible hostile Git configuration; the remaining allowlisted Git investigation commands still run inside Pi's existing project Trust boundary.

## Theme

Add the included theme to `~/.pi/agent/settings.json` while keeping your existing settings:

```json
{
  "theme": "github-dark-default"
}
```

Pi will load the extensions and theme the next time it starts. OpenPI's Background, Subagent, and Workflow Skill files remain in the package, but ordinary turns do not advertise them in the system prompt; the matching path is disclosed only after explicit capability intent or after the model loads that group through the opt-in adaptive gateway.

The terminal theme above remains Pi-owned. OpenPI Web has separate package-owned appearance preferences: `system`, `light`, and `dark` modes; chat width from 820-2000px; chat font size from 12-24px; and whether thinking blocks start expanded. `system`, 820px, 14px, and collapsed are the defaults. The complete `ui.webAppearance` object defaults to `{ "palette": "default", "accent": "", "background": "", "foreground": "", "font": "codex" }`. Palettes are `default`, `mist`, `rose`, and `pine`; fonts are `codex` (Codex default), `sans`, `serif`, and `mono`. Legacy `system` maps to `codex` when reading configuration or importing a theme. The default stack is `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`: SF Pro with PingFang on macOS, Segoe UI first on Windows, and the platform sans-serif fallback elsewhere. No proprietary font files are bundled. Each color must be empty (use the theme default) or `#RRGGBB`. The object is replaced as a whole, with every field required and unknown fields rejected. The legacy `ui.webTheme` values `mist`, `rose`, and `pine` remain valid and take precedence as old presets; replace them by saving a new mode together with the appearance object. Web controls save these presentation values directly through the shared validated configuration writer and apply the saved response without a model turn or chat message. They remain available during running turns and Plan mode. `/openpi-setup` can also change the same values through `ui_web_appearance`; its no-argument status reports the palette, theme-default or custom colors, and font. Both paths share `my-pi-setup.json`, locking, validation, unknown-field preservation, and atomic persistence.

The optional [OpenPI Browser Bridge](web/browser-extension/README.md) 0.4.0 supports Chrome, Edge, Brave and Chromium 145+ plus native tabs in macOS Safari 26+ and Firefox 128+. The Browser settings page guides one step at a time in a separate window: open the browser's settings, locate the illustrated control, select the bundled extension, then connect. Document Picture-in-Picture keeps the guide floating where supported; otherwise it uses a normal popup, with an inline fallback if blocked. Safari uses Add Temporary Extension in Developer settings; Firefox uses Load Temporary Add-on on about:debugging and selects manifest.json. These temporary installations must be reloaded after browser restart; permanent distribution needs signed packages. Chromium uses Developer mode and Load unpacked. The actual browser must confirm installation and site access. Only a matching live handshake reports Connected; advancing a step never grants control. Embedded control and navigation enhancement require Chromium. Safari/Firefox expose DOM semantics and screenshots of native tabs; nested frames must be opened separately.

Exit Plan mode before starting `/openpi-setup`, including from Web settings. The command checks the current Session branch before starting a setup turn, and queued requests are checked again before delivery. Web disables package configuration controls during planning and offers the existing Plan exit action once the Session is idle; exiting does not start a model turn or authorize implementation. Settings reports the latest setup episode from persisted tool receipts, including unchanged saves, failures, cancellation, and an unconfirmed save. A completed turn or an assistant's claim alone is not proof that configuration was saved.

## Configure this package

Web appearance controls directly save only their presentation fields; their success status is based on the completed write. Other package-owned settings forms submit requests through `/openpi-setup`. Role/model choices, concurrency, skill and plugin configuration requests remain visible in that episode, including required confirmation and its final apply/closure receipt. A setup submission message is not proof of persistence. Pi-owned model definitions and credentials have separate direct forms backed by Pi's `models.json` and native login API; secrets never enter the setup prompt.

The Web model page offers Account, Third-party providers, and Custom model API when adding a connection. Account choices come from Pi's registered OAuth providers. Browser, device-code, and manual callback interactions are shown only when requested by that native provider. Only the idle active Session may start sign-in; settings navigation stays locked until the native flow settles, including after cancellation. Existing accounts support reauthentication and confirmed sign-out. Pi owns the shared credential store; signing out also affects other Sessions using that credential. A configured credential does not prove endpoint availability. Credential persistence and model-list refresh are reported separately if the latter fails. These controls introduce no OpenPI preference or second account store.

After saving a connection, choose a model for the current Session and optionally make it the default for new Sessions. The separate New-session default row reads and writes Pi's global `settings.json` through its native SettingsManager, confirming persistence before displaying success. Changing only this default leaves existing Sessions unchanged; trusted project model overrides are displayed separately. Current-Session selection uses Pi's Session model and exact provider/model identity, so identical model names on different connections remain distinct. Provider marks use restrained brand accents. Pi keeps one credential per provider ID; reauthentication replaces it, while distinct custom connections use distinct IDs.

Web shows the original setup command and its results, including failed or unapplied requests, rather than hiding the configuration episode. Appearance controls wait for the current run to settle before accepting another change. Chat-width and font-size reset buttons request the existing defaults through the same setup entry point. The model tree selects the editable Pi definition and retains unsaved drafts within the same Session; narrow screens use a labeled settings-section selector.

In the TUI, setup requests default to `[OpenPi] <command>` and the original user request (including the `my-pi-setup` alias); long or multiline requests wrap naturally. Pi's `app.tools.expand` action (`Ctrl+O` by default) shows the complete original prompt through native rendering. Expansion is host-owned: hosts without a custom-message disclosure-click API do not offer a click toggle. Legacy or invalid command/request metadata falls back to Pi's full native display. This is presentation only: Session content, model input, setup authority, and receipts are unchanged. Web keeps its existing command/request projection; RPC/JSON and HTML exports retain the full prompt rather than the TUI summary. See [Issue #654](https://github.com/openpi-dev/openpi/issues/654).

Each delivered setup request explicitly announces its new episode. Success and closure messages apply only to their completed episode; a later `/openpi-setup` request can activate the writer again without reusing the prior episode's authority.
The `compact` footer preset resolves to `plain` style with the default single-row layout; it is not a separate stored style. Applying it to the default footer does not change its appearance. Successful setup receipts distinguish saving the document from changing effective settings and list only fields that actually changed. Keeping defaults without invoking the writer does not create a file.

Explicit field assignments retain their meaning: `footerStyle="compact"` is invalid; the allowed styles are `plain`, `powerline`, and `powerline-mono`. Setup should explain the legal choices and wait for a valid choice instead of silently applying a preset or default. Requesting the `compact` preset is valid and resets both style and layout. Tool writes reject invalid footer styles and presets; stored invalid styles block writes rather than being repaired automatically.

The personal `my-pi-setup.json` document uses `configVersion: 1`. A missing file uses built-in defaults without creating a file. Unversioned documents migrate only on an explicit save. Malformed JSON, read errors, unsupported versions, and invalid known fields block writes and are reported by `/openpi-setup`; rendering uses safe defaults while the file remains intact. Repair the file, or explicitly remove it to reset. Unknown fields are warned about and preserved; changes that would remove unknown fields are rejected. Diagnostics show field paths, not raw values or post-edit command contents.

On Session start or extension reload with a UI available, OpenPI issues one brief notification if configuration loading has errors or warnings, directing the user to `/openpi-setup` for full diagnostics. Errors explicitly report the safe-default fallback and blocked writes; legacy documents and unknown fields produce a warning. Missing or valid current-version files stay quiet. This check does not start a model turn, expose the writer, or modify the file. Non-UI callers can obtain diagnostics through the existing setup command.

Setup saves under the existing cross-process lock and waits for current-session configuration consumers to apply. An apply failure restores the previous document and reapplies its configuration, provided the file still matches this write. Concurrent external changes are preserved; an incomplete recovery is reported as an error. This is not an atomic update of all running Pi processes or a crash-recovery journal. No additional setup command, preview UI, or statusline package is required.

Use the single canonical package-owned command. `/my-pi-setup` remains a compatibility alias. With no arguments, the current model explains the configurable areas and uses `ask_user`: first run initializes them; later runs explain the saved state and ask whether to keep it, change one area, or review everything. With arguments, it treats the rest as a targeted natural-language request. Persist still goes through the typed `configure_my_pi_setup` tool. The writer stays hidden while a busy Session queues the setup request, becomes active only when that exact request is delivered to the model, and is hidden again afterward. One successful apply completes the episode. If the run settles without a successful apply, OpenPI appends a visible, durable closure receipt to the Session and later model context; it says that the writer is hidden and re-entry requires `/openpi-setup <request>`. OpenPI also verifies that the active writer belongs to the package source before announcing an active setup episode; duplicate or mismatched sources fail closed without injecting the setup request. A later configuration change starts a new episode with `/openpi-setup <request>` rather than reusing the hidden tool:

Capability discovery defaults to `explicit`, preserving the zero-resident OpenPI tool surface until the user asks for a capability. The case-insensitive English words `subagent` and `workflow` are reserved authorization words: entering either word is sufficient to load its capability group, and the interactive editor shows it in Claude Code-style lavender before submission, with a darker purple fallback for light themes. This makes discussion that contains either English word an intentional opt-in tradeoff; conditional and negated clauses remain inert, while Chinese capability names still require a recognized action request. `adaptive` is an explicit opt-in that keeps only `openpi_load_tools` visible and allows the model to load a useful group on its own; because this can start Subagents, Workflows, or background processes, normal permission and configured concurrency/call limits still apply. Changing the setting updates the current Session immediately, while already loaded groups remain stable for that Session. Accepted Suggestion text is classified only after it becomes real editor input. The visual feedback and runtime activation share one fail-closed intent classifier. Next-action suggestions default to off. Run `/openpi-setup` to explicitly choose an available model and reasoning level. After a fully settled main-agent run, one suggestion may appear as dim inline text on the first row of an empty editor; reserved cells at the row end keep CJK IME preedit from overwriting it. `Right` accepts it into the editor without submitting, while any other editor input dismisses it. Suggestions are ephemeral and never enter session history or model context. Workflows default to 8 concurrent agents and 128 total agent calls per run; configurable hard maxima are 64 and 1024. A separate `child_execution_limit` is off by default. When explicitly set to 1-64, it is a FIFO cap on active child executions shared only by Workflow, Direct Subagent, and BTW within one top-level Pi Session; their existing Workflow 8/local call limits, Direct pool 4, and BTW pool 2 remain in force. A dormant child, parent Session, Background Terminal, model request, token, cost, and provider quota do not consume this limit. `/subagents` shows the shared limit, held/queued counts, origin counts, and generic blocking reason without exposing task text. Reducing the configured limit below live held slots is rejected and rolled back; cancellation and shutdown reject queued attempts but do not claim an active child has stopped before its actual terminal lifecycle settles. The large decorative header defaults off and the custom dashboard footer defaults on with a one-line plain layout (`model context |flex| git pr cwd`; `thinking`, `cache`, `cost`, and `throughput` remain opt-in metrics). Footer presets are `powerline`, `powerline-mono`, and `compact`; style can also be set independently to `plain`, `powerline`, or `powerline-mono`. Custom layouts use a 2D `footerLines` array with at most one `flex` per row for left/right alignment. Nerd Font affects powerline separator glyphs (``) and adds Codex-style outline icons to compact read, terminal, edit, search, and directory activity rows; all accompanying text remains readable without it. Footer metrics use one Codicon outline family (`` model, `` context, and `` directory) plus `⎇` for the branch. A Nerd Font containing Codicons renders them as designed; without one, the text labels remain readable even if an icon falls back to an empty box. Footer changes apply immediately in the active TUI session. Subagent results default to a compact status summary; full mode remains available as a per-user setting, and `app.tools.expand` (`Ctrl+O` by default) reveals the available child report. Ordinary `read`, `grep`, `find`, and `ls` operations render as one-line semantic activity summaries. Bash and Write/Edit default to the same activity-row projection, showing the target, running/success/failure state, and useful line or diff counts without replaying stdout or previews. Select full independently for Bash or Write/Edit to keep Pi's native rendering expanded. `app.tools.expand` temporarily restores the native arguments, output, errors, diff, timing, images, truncation notices, and full-output metadata; it never changes Session history or model context. An optional post-edit command is off by default: set one (for example `npm run format`, maximum 500 characters) and it runs once in the background after each interactive-TUI turn with successful Write/Edit operations, with failures reported as a notification. It deliberately does not guess whether arbitrary Bash commands changed files. Built-in Agent roles `explorer`, `implementer`, `reviewer`, and `advisor` are shared by `subagent_spawn.agent_type` and Workflow `agent(..., { agent_type })`; all inherit the parent model and currently active child-eligible tools by default. Explicit custom role `tools` lists narrow that surface; omitted lists inherit it. Built-in investigator roles suggest read-only work but do not impose a read-only tool boundary outside Plan Mode. Existing role files are preserved, so an old global `explorer.md` allowlist continues to exclude Bash/network tools until deliberately edited. `/openpi-setup` may assign a currently available Registry model to any subset; clearing one returns it to inheritance and omitted roles stay unchanged. Model precedence is explicit call > selected role-file model > setup assignment > parent inheritance; effort is explicit call > selected role > parent. A trusted project `.pi/agents/<role>.md` overrides global `~/.pi/agent/agents/<role>.md`, which overrides the complete built-in role definition. Normal overrides appear as an informational `Agent roles` summary with aligned role names and home-relative source paths; only the effective definitions are shown. Invalid files, unavailable tools, and blocked fallbacks remain separate warnings, with their source and diagnostic detail. Role-model changes apply to the next spawn or Workflow agent call without reload. Configuration is stored privately at `~/.pi/agent/my-pi-setup.json`.

A disabled master switch rejects every model browser operation, including during active turns, while ordinary iframe browsing remains available.

Browser choices are `embedded`, `chrome`, `edge`, `brave`, `chromium`, `safari`, and `firefox`. Choosing a default does not grant access. Safari/Firefox use a separate portable extension build with the same OpenPI tool and permission lifecycle; the Pi core and upstream pi-computer-use package are unchanged.

Web model configuration can query an explicitly supplied provider connection, search its model catalog and add up to 100 selected models in one revision-checked native `models.json` write. Existing model metadata and credentials are preserved. Discovery uses Pi credentials only for the matching saved endpoint, or an optional temporary key that is not persisted. Catalog queries are bounded to ten seconds, 1 MiB and 500 models, reject redirects, and never send prompts. New models inherit the form's context/output and reasoning defaults; verify these in advanced parameters. Manual configuration remains available when the catalog is unsupported. No additional OpenPI preference is introduced.

### Post-edit lifecycle

Use a finite, foreground command such as `npm run format`, not a watcher, server, or detached background writer. Post-edit remains off by default and runs only in the interactive TUI, once per settled turn with successful native Write/Edit operations. Bash is not inspected for file changes.

The next Agent start (including a background completion's parent wake-up) waits for outstanding commands to finish, and all tool calls in this Session also join them before executing. This includes read-only and custom tools: a tool-name allowlist cannot reliably identify every workspace reader. Tools that do not access files wait too; only successful native Write/Edit results schedule post-edit. Nonzero exits and interrupted commands produce bounded, sanitized notifications; neither triggers an automatic repair loop or a test-acceptance gate. A command that does not exit can keep the next turn waiting: there is no automatic timeout that silently releases this boundary. Canceling the waiting Agent releases its wait without permitting its tool call or forgetting the still-running command; session teardown can then request command cancellation.

Each queued run captures its command and working directory at settlement. Configuration changes affect future runs; disabling post-edit discards queued runs but lets the active command finish. Session start/shutdown discards queued work and requests cancellation, without treating an abort request as process completion. Results from the old session do not notify the new one.

This coordinates one extension instance's foreground commands with its Agent. It does not lock the workspace against other Sessions, Subagents, external editors, user shell commands, or detached descendants. Pi's command cancellation does not guarantee termination of an entire process tree; keep all command writes in the foreground and inspect interrupted work before relying on its files.

## pi config checkboxes: self-contained sets

`pi config` shows OpenPI as a flat list of resources to tick. The list shows what exists, not what depends on what, and excluding the wrong entry takes its tools with it without an error. This section projects that flat list onto the capability groups the runtime already defines, so the loading boundary is visible before the first run instead of at the first missing tool. Set names reuse the runtime's own `OPENPI_CAPABILITY_GROUPS` and intent vocabulary; no second naming system is introduced.

Resolved in this checkout at OpenPI 0.10.0 (`78dc574`) the list is **35 extensions, 4 skills, and 1 theme**. Treat that as a resolution result, not a fixed property: the extension entries are whatever `extensions/*/index.ts` matches under the `pi.extensions: ["./extensions"]` manifest (`package.json:48`), and the skill entries are the package's `skills/*/SKILL.md` files plus any workspace-local skill (here `.agents/skills/test-value`). The tables below are a projection of these runtime definitions; a change to the extension list changes the projection, not the method.

### What a checkbox actually controls

Filtering is load-time inclusion, not dependency resolution. Pi loads exactly the entry files a filter allows, and excluding one entry does not remove its sibling modules, so a surviving extension that imports across directories still resolves.

Measured on 0.10.0 at `78dc574`: **45 filter combinations** — single-extension exclusions, directory-granularity exclusions, skill/theme exclusions, and near-empty sets. Of those, 29 were resolved through Pi's package manager and resource loader, 39 were started through `pi --mode rpc`, 23 did both, and the remaining 16 saw only the rpc path. Every run exited 0 with empty stderr, and all 29 loader runs reported **zero extension errors**. They are not 29 independent results: several configurations coincide, and the 29 collapse to **22 distinct load outcomes**.

One of those coincidences is the more useful finding. The three directory-granularity exclusions (`!extensions/file-search` and friends) excluded **nothing**: each still resolved 35 extensions, byte-identical to the unfiltered baseline, because the manifest globs `extensions/*/index.ts` while a directory-level negation matches no entry. An exclusion that reads as valid and silently keeps the extension is the failure mode this section is about, so treat "the filter looks right" as unverified until the resolved count moves.

`git-read` keeps working when a *single-entry* exclusion removes `extensions/file-search/index.ts`, because it still resolves `../file-search/src/output.ts` (`extensions/git-read/index.ts:23`) — the filter removed the entry, not the module.

The practical consequence is the opposite of a safety net: **excluding the wrong set fails silently.** A capability group whose owner was excluded simply never produces its tools. The loader reports no error and no diagnostic for this (`loader.getExtensions()`, `getSkills()`, and `getThemes()` all keep empty `errors`/`warnings`/`diagnostics` lists), and nothing on stderr announces it.

There is one runtime signal, and it is easy to misread. An explicit gateway request for a group whose owner is absent returns an empty activation set — `activatedTools: []` with the text `Activated tools: none yet.` (`extensions/capabilities/index.ts:201-204`, the `none yet` fallback at `:203`). That wording reads like deferred activation, so "none yet" can be mistaken for "not yet, try again" when it means "never, in this configuration". The same call still advertises the capability's skill file (`:73`, via `skillGuidance`), which points at guidance whose tools are not mounted. So: no startup error, no loader diagnostic, and a gateway reply that only distinguishes the two cases if you read `activatedTools` rather than the sentence.

Registered and active are also separate layers, which is why a checkbox can look inert. A session that has loaded nothing still registers the OpenPI tool definitions; what the gate decides is which of them are projected into the active surface. In the default `explicit` configuration none of the capability-owned tools are active, and the gateway itself is not active either — it appears only after an explicit request (`extensions/capabilities/index.ts:168`) or under `adaptive` discovery (`:111-119`). With `capabilities` excluded, the gateway is not merely inactive: **its registration is gone too**, because the extension that registers the classifier and the gateway is the one that was unticked. That is the mechanical reason the loss is silent rather than reported.

### npm dependencies do not track the checkboxes

**A checkbox is a loading boundary, not an installation boundary.** OpenPI declares its runtime dependencies unconditionally in `package.json`, and the `pi` manifest carries only resource paths — `extensions`, `themes`, and `image` (`package.json:47-55`) — so there is no per-resource dependency declaration for a filter to act on. In this checkout those dependencies are seven, and they are concentrated rather than distributed per set: `effect` reaches `ask-user`, `background-terminals`, `file-search`, `git-info`, `git-read`, `subagents`, and `suggestions`; `@effect/platform-node` reaches `file-search`, `git-info`, and `git-read`; `acorn` reaches only `workflows`; `undici` and `node-pty` are used under `web/` and `jiti` by the `bin/` entry point; `@effect/platform-node-shared` is declared with no production import outside `tests/`.

Consequently unticking `workflows` still installs `acorn`, and unticking every `effect`-based extension still installs `effect`. There is no per-set npm dependency to satisfy — and no dependency pruning either. The Pi packages (`@earendil-works/pi-ai`, `pi-coding-agent`, `pi-tui`) and `typebox` are peer dependencies supplied by the host, so they do not vary with tick state at all.

### Choosing by intent

The sets exist so the choice can be made from intent rather than from a dependency table. The runtime already classifies the same intents at `extensions/shared/capability-intent.ts:7`; asking for a capability in these terms is what loads it. Read this table first; the reference tables below exist to justify it, not to be memorized.

| Your intent | What to tick | What that means in practice |

### Re-deriving these tables

The tables above are a projection of runtime facts, not a second source of truth. Two claims are worth re-checking whenever the extension list changes, because both are invisible to a plain source read:

1. **The set list.** `OPENPI_CAPABILITY_GROUPS` at `extensions/shared/tool-surface.ts:76` and the tool ownership map at `:11` are the authority. A new capability group appears there first, and a new `OPENPI_OWNER_SOURCE_PATHS` entry (`:147`) is required before any extension can own it.
2. **The activation outcome.** Tick state is resolved by Pi's own package manager, and activation can be observed without a provider by resolving resources and then driving `before_agent_start`. The two conclusions most likely to invert are "which extension is the sole gate" and "which imports actually constrain the checkbox" — hence the `capabilities` and `workflows` rows. Re-run both against a real `createAgentSession` as well, because the activation harness fakes the session object and would not catch a difference that only the real loader produces.

No separate generator or frozen fingerprint is introduced here, and that is a deliberate scope decision rather than an oversight. This section is a projection of the runtime's own definitions — `OPENPI_CAPABILITY_GROUPS` and `OPENPI_OWNER_SOURCE_PATHS` are the single source of truth — so a drift guard would guard a table that is already derived. What it would not do is catch a table that quotes the runtime correctly and reasons about it wrongly, which is the failure this section actually had; that is caught by re-measuring, not by a hash. Keeping the section free of build steps also keeps `SETUP.md` a document rather than a generated artifact that has to be regenerated before release.

The anti-drift convention is therefore human and stated: treat any row as stale the moment the cited `file:line` stops matching, and re-measure rather than editing the conclusion in place. Automated fingerprint freezing and a shared schema with `check-docs-contract` were considered and left out of this change; the repository's machine-checked documentation contracts (`scripts/check-config-contract.mjs` for the 37 persisted configuration fields, `scripts/check-docs-contract.mjs` for `docs/decisions`) do not cover this section.

The evidence column uses four levels of verified evidence, plus one that says so outright. Faked and real evidence are kept apart on purpose, because they do not measure the same code path:

- **verified (source)** — the claim is fixed at the cited line. Nothing was executed.
- **verified (runtime-resolver)** — Pi's own package manager and resource loader (`DefaultPackageManager.resolve`, `DefaultResourceLoader.reload`) resolved the entries. Real code, but it observes *loading*, not tool activation.
- **verified (fake harness)** — a fresh-session activation harness drove `before_agent_start` and read the resulting active tool set, but against a **hand-written fake `ExtensionAPI`**, not a Pi session.
- **verified (real session)** — a real `createAgentSession` with `DefaultResourceLoader(additionalExtensionPaths)`.
- **not verified** — stated as a limitation, and never inferred to follow from green checks elsewhere.

The fake harness is not a weaker version of the real one; it exercises a *different branch*. It never registers tools, so `getAllTools()` returns entries with no `sourceInfo`, which sends `extensions/shared/tool-surface.ts` down the "every tool lacks sourceInfo" fallback at `:277`. A real session reaches the `sourceInfo.path === expectedSource` branch at `:283-292`. It also starts from a fully-populated active set rather than an empty one, so "activated" there is a set difference against a non-default baseline. Treat the fake-harness rows as evidence about the entry/deferred mapping, not about real ownership resolution. Where a claim matters for a real session, it was re-run there.

The two `not verified` rows are the honest boundary of this section. Tick state was never driven through the real `pi config` TUI, and no provider was ever called, so nothing here describes how a live model behaves once a set is loaded. The filter shape itself is no longer an assumption. `pi config`'s selector does not write this section's probe syntax; it writes an **entry-level relative path** with a `-`/`+` prefix. For a package resource the pattern is `relative(packageRoot, resourcePath)` (`dist/modes/interactive/components/config-selector.js`, `getPackageResourcePattern`), so unticking `subagents` appends `-extensions/subagents/index.ts` to that package's `extensions` array. Driving that exact shape through Pi's resolver confirms it works: the excluded entry drops out and the rest resolve cleanly (34 of 35, 0 errors), and unticking two appends two such lines (33 of 35). Prefixes are not interchangeable: `-extensions/subagents/index.ts` (the shape the TUI writes) and `!extensions/subagents/index.ts` both exclude the entry (34 of 35, 0 errors), while the directory form `!extensions/subagents` excludes nothing (35 of 35, identical to the baseline) and the additive `+extensions/subagents/index.ts` changes nothing because the package already declares it. So the no-op finding above is specifically about **directory-level** negation, not about negation in general. The remaining gap is only the keystroke path itself — no TTY was available to press the key — but the write shape, the string it produces, and that string's effect on resolution are all measured.

## Session Goal and Tasks

`/goal`, `/goal <objective>`, `/goal edit`, `/goal pause`, `/goal resume`, and `/goal clear` implement a branch-scoped persistent objective with the current OpenAI Codex Goal semantics. `/goal <objective>` starts immediately with no second success-condition prompt or admission judge; the objective can contain up to 4000 characters. `/goal` shows status, objective, elapsed time, consumed tokens, optional token budget, and status-specific command hints. Replacing unfinished work requires `Replace current goal` confirmation, while a complete goal is replaced silently. Editing preserves usage and the optional budget; it reactivates complete or budget-limited goals only when the preserved budget is not already exhausted.

Model callers use `get_goal`, `create_goal`, and `update_goal`. `create_goal` is only for an explicitly requested persistent autonomous goal and fails while an unfinished goal exists. `update_goal` can only mark `complete` after a strict requirement-by-requirement evidence audit, or `blocked` after the same genuine blocker repeats for at least three consecutive Goal Turns. User/system operations own pause, resume, clear, usage limits, and budget limits.

There are no normal user-facing Turn, no-progress, or wall-clock caps; a hidden 1000-continuation circuit breaker exists only to stop runaway automation. An optional `token_budget` must only be positive. Goal non-cached Assistant input-plus-output Token and elapsed-time usage are persisted; crossing the budget marks `budget_limited` and queues one wrap-up Turn. Active goals continue after reload/resume. Fork and tree navigation defer inherited active continuation until the first explicit user input; paused, blocked, and usage-limited goals remain stopped and can prompt for Resume. A v1 active/waiting goal migrates once to paused. Assistant aborts pause an active goal and Assistant errors block it. Print/json automation is inert. Footer text mirrors Codex (`Pursuing goal (…)`, resume hints, `Goal unmet`, `Goal achieved`) without showing the objective or legacy Turn counts. An achieved Footer remains visible until the next explicit interactive/RPC input, then a branch-persisted acknowledgement hides only the Footer while `/goal` retains the completed record.

Session Tasks remain advisory multi-item work intent and do not determine Goal completion. They are scoped to the current request batch: once every item is done or dropped, the batch closes and the next `tasks_add` starts again at T1. The model marks a tracked item `in_progress` before starting it, records `done`, `blocked`, or `dropped` immediately after that item reaches a real outcome, and reconciles touched items before its final answer. Every add/update result returns the complete bounded current snapshot so the next item is explicit and the panel refreshes on each persisted transition. Commit, test, and authorization signals are only task-scoped evidence candidates; OpenPI never infers completion or mutates a task from those signals. Active items persist in a polished Claude Code-style panel above the editor; `Ctrl+Shift+T` or `/tasks hide|show|toggle` controls visibility, while `/tasks` opens the full list. No `/openpi-setup` setting or secondary judge model is required.

## Other commands added by this fork

- `/sessions` searches and previews project sessions before switching.
- `/tasks` inspects branch-scoped advisory work items.
- `/goal ...` controls the persistent autonomous session objective.
- `/context-pivot <next phase>` deliberately compacts a long current session into a next-phase brief. It requires at least 30,000 context tokens and is rejected below that; use `/sessions` to browse or switch sessions, or install the optional `pi-intercom` package for communication between top-level sessions.
- `/cron every <5m> <prompt>`, `/cron in <30s> <prompt>`, `/cron list`, and `/cron remove <id>` schedule a prompt for this session. Jobs are in-memory and session-scoped (cleared on shutdown), fire only while the session is idle, and use a duration grammar (`30s`/`5m`/`2h`, minimum 30s) rather than crontab fields, because the scheduler polls about every 30 seconds. Jobs due in the same poll are delivered as one triggered turn while retaining each job's id and recurrence metadata; if that atomic delivery fails, every due job remains pending for retry.
- `/plan [objective]` explores read-only before changing anything and automatically loads the `search` capability for the current Session. While armed it blocks `edit`, `write`, mutating Bash, raw Git diff-rendering commands, `subagent_send`, `workflow`, and `bg_start`; read/grep/find/ls/fd/rg, `git_log`/`git_diff`/`git_show`, and verified non-diff Git/GitHub Bash commands stay available. It permits `subagent_spawn`, but the harness narrows every newly spawned planning child to investigation-only tools; agent types can narrow that list further, never widen it. The model must submit the complete plan through parent-only `plan_ready`; the write gate stays closed until `/plan` prepares an editable implementation prompt for the current or a fresh Session. `/plan off` cancels.
